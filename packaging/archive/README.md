# archive

One signed apt archive root per licensable unit, plus the key that signs them.

Serving them, and deciding who may fetch from which root, is not here. This tooling stops at
producing the tree.

## Layout

One archive root per licence, not components inside one archive. A gated component makes apt fetch
an `InRelease` advertising paths it then gets 403s on, and it reports that as a broken repository
rather than "not for you".

`publish_archives.sh` writes one root per entry in `../archive/lists/`, which
`workspace/gen_release_set.sh` derives from what each package declares:

```
dist/public/            the root named "public", served to anyone
dist/private/<root>/    every other root, one tree each
```

A root is whatever a package declares, so adding one needs no configuration beyond the package
declaring it.

## Run order

Given `.deb` files in `out/` and package lists in `lists/`, produced by
`workspace/gen_release_set.sh`:

```bash
docker run --rm -it \
  -e HOST_UID=$(id -u) -e HOST_GID=$(id -g) \
  -v "$PWD:/work" -v "$PWD/out:/out" \
  -v "$PWD/../builder/out:/builder-out" \
  -v "$PWD/dist:/dist" \
  -e ALLOW_THROWAWAY_KEY=1 \
  ubuntu:24.04 /work/publish_archives.sh
```

The result is `dist/`, a tree of signed archive roots. Point a gateway at it to serve them.

## Letting something else publish

`add_and_publish.sh` is the entry point a pipeline calls: it routes delivered packages into their
roots, publishes, and reads the index back. It refuses a root that disagrees with the
`<duatic_archive_root>` the package declares, which `build_pkg.sh` carries into the binary, so a
caller cannot route a licensed package into the open archive by asking.

That check binds a package to its root. It does not bind a *caller* to a root, and on a host with
one key every caller can reach every root. `publish-gate` is the forced command that does:

```
command="/usr/local/bin/publish-gate products/example",restrict ssh-ed25519 AAAA... example
```

The permitted roots come from that line rather than from the request, because `authorized_keys` is
the one place the caller cannot edit. A key pinned to one root cannot reach another, cannot reach
the open archive, and cannot run anything else on the host.

This is host state. It is not in this repository and is not reviewed when this repository is,
which is the point: what is being constrained must not be able to edit the constraint. It also
means a rebuilt host without it fails open, so whatever restores that host has to restore this.

## The signing key

Every client pins this key with `Signed-By`, so it is the single thing they all trust. Losing it is
not a local problem: apt on every machine rejects the archive, and the replacement keyring cannot
be shipped through the archive that is broken.

`publish_archives.sh` therefore refuses to run when no key is present. `ALLOW_THROWAWAY_KEY=1`
opts into generating one, which is right for local work and wrong everywhere else. Set
`EXPECTED_KEY_FPR` is required unless that opt-in is set, and publishing fails if the key is not the
one clients pinned.

`make_archive_key.sh` creates a real one. Run it once, on a machine that is not the publish host:

```bash
./make_archive_key.sh ~/archive-key
```

It writes a certification-only primary key, a signing subkey, a revocation certificate, the public
keyring for clients, and the subkey on its own for the publish host. The publish host imports only
the subkey, so it can sign and cannot certify: a compromised host is handled by rotating the
subkey, not by reissuing the identity every client has pinned.

That key has a passphrase, and `publish_archives.sh` signs under `-batch`, where gpg cannot ask for
one. `GPG_PASSPHRASE_FILE` names a file holding it, readable only by the publishing user. A file
rather than an argument, so it does not appear in `ps`.

A passphrase the publish host can read does not defend against someone who already has that host.
What it defends is the keyring on its own, in a backup or a stray copy.

The key generated by `ALLOW_THROWAWAY_KEY=1` is not a production key. Before anything depends on it:

- **Generate it off the build machine and keep it there.** A runner that can read the key can sign
  a package that every client installs as root.
- **Protect it.** The generated key uses `%no-protection`, so it is a plain file. Production wants
  a passphrase at minimum, a hardware token or KMS preferably.
- **Make a revocation certificate at creation time** and store it separately. The generated key has
  `Expire-Date: 0`, so nothing expires it for you.
- **Ship the keyring in the base image and update it as a keyring package.** apt accepts a keyring
  holding several public keys, which is what makes rotation possible: publish the new key, wait for
  it to land, then start signing with it.
